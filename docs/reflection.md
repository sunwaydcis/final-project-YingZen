# Personal Reflection on Object-Oriented Programming and Application Design

This reflection outlines the software engineering processes, OOP applications, challenges, and overall evaluation of the SDG-1 Microfinance Loan Tracker application.

## 1. OOP Applied
The development of this microfinance tracker heavily leveraged core object-oriented principles to ensure code modularity, reuse, and clarity. Inheritance was implemented using a `sealed trait Loan` as a common base type, which was extended by `StandardMicroLoan` and `EmergencyInterestFreeLoan`. This architecture allowed the separation of interest-calculation logic, promoting encapsulation. Subtype polymorphism was demonstrated through explicit method overriding, specifically in overriding the `totalRepayment` method of `EmergencyInterestFreeLoan` to bypass default interest additions and apply flat administrative fees instead. Parametric polymorphism (generics) was utilized to construct the data persistence layer. A generic `CSVSerializer[T]` trait and a `CSVDataStore[T]` class allowed the application to handle files for different types of entities without repeating file-writing code. Encapsulation was enforced using private fields with adjacent documentation explaining their restriction, separating raw filesystem paths from outer controllers. Furthermore, domain classes were modeled strictly as immutable case classes, guaranteeing that state transitions only occur through clean reactive bindings in the GUI layer.

## 2. Problems Encountered
One major technical challenge was managing application state safely under strict immutability constraints. The rubric forbade the use of any mutable variables (`var`) or collections (`ArrayBuffer`, `ListBuffer`, `Array`) in the domain code. Initially, syncing updates between the user inputs and the lists of borrowers proved difficult because typical JavaFX designs rely on mutating lists directly. To solve this, ScalaFX's `ObservableBuffer` was employed to bridge the gap. By binding the immutable model objects into the reactive `ObservableBuffer`, data could be updated thread-safely in the GUI layer while keeping the domain classes pure. Another challenge was dealing with type-safety in standard alert popups, where `headerText` and `contentText` assignments clashed because of ambiguous method overloading in ScalaFX's Java wrappers. This was fixed by explicitly passing `None` as an `Option[String]` to the dialog builders, clarifying compiler ambiguity and ensuring warnings were silenced.

## 3. Strengths and Weaknesses
A major strength of the design is its clean separation of concerns. By segregating the codebase into models, persistence, and UI controllers, the application remains maintainable and dry. The use of generics in the persistence layer means that adding new CSV data stores requires minimal effort. However, a primary weakness is the reliance on flat CSV files for data storage. While functional for small microfinance operations, large-scale systems would suffer from slower retrieval rates and concurrent access conflicts. If the system was scaled, a proper relational database using JDBC would be required to handle transactional safety and complex relational queries between borrowers and loans.
